# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-tenant Flask web app ("Tracking Validation Dashboard") for LMWN/LINE Pay analytics tracking QA. A user uploads a tracking spec sheet (CSV/XLSX), the app queries Trino for matching event data, uses Gemini to auto-generate Great Expectations (GX) rules from the spec, validates the data against those rules, and produces a PDF report per batch.

The active, actively-developed entry point is **`app_flask.py`**. `app.py` is an earlier Streamlit implementation of the same tool — it hasn't been touched since the initial commit and should be treated as legacy/reference only, not as a place to make changes.

## Commands

Run the app:
```bash
python3 app_flask.py        # serves on http://localhost:5050, debug=True
./kill_server.sh            # kills whatever is bound to port 5050
```

Install dependencies:
```bash
pip install -r requirements.txt
pip install flask            # NOT in requirements.txt but required by app_flask.py — install manually
```

There is no test suite, linter, or build step in this repo.

### macOS / WeasyPrint

PDF generation uses WeasyPrint, which needs native `pango`/`cairo`/`glib` libraries (`brew install pango cairo glib gdk-pixbuf` on macOS). `app_flask.py` patches `DYLD_FALLBACK_LIBRARY_PATH` to `/opt/homebrew/lib` at the top of the file *before* importing `weasyprint` — if you add a new entry point or script that touches PDF generation, replicate that same fix before the `import weasyprint` line or the import will fail with a `libgobject` `dlopen` error.

### Environment (`.env`)

Required variables: `TRINO_HOST`, `TRINO_PORT`, `TRINO_USERNAME`, `TRINO_PASSWORD`, `GEMINI_API_KEY`, `GEMINI_MODEL_ID` (defaults to `gemini-2.5-flash` if unset). If `GEMINI_API_KEY` is absent, AI generation is silently disabled (`GEMINI_AVAILABLE = False`) rather than erroring.

## Directory layout gotcha: several dirs are gitignored but load-bearing

`sql/`, `expectations/`, `logs/`, `reports/`, and `gx/` are all in `.gitignore` — a fresh clone will not have them (they're auto-created empty by `app_flask.py` on startup, except `gx/`). In this checkout they already contain real, actively-used content:

- `sql/*.sql` — per-data-source query templates (`web.sql`, `food_main.sql`, `mp.sql`, `topup.sql`, `native.sql`, `kyc.sql`), selectable in the "configure" step. Each contains `{dt}` and, in some cases, `{extra_where_conditions}` format placeholders filled in by `run_validation_process`.
- `expectations/*.json` — GX expectation suites, one per `suite_<event_type>_<placement_id>`, generated by the AI worker and persisted here so GX can reload them.
- `gx/` — the actual Great Expectations `FileDataContext` root (`gx/great_expectations.yml`, `gx/checkpoints/`). Pandas datasources are registered here dynamically per run (`pandas_ds_<batch_id>_<segment>`), so this file accumulates entries over time and is never pruned.
- `logs/` — one JSON dump of the full checkpoint result per validated spec (or per error), named `run_<batch_id>_<event>_<placement>_<uuid8>.json`.
- `reports/` — generated PDFs, named `report_<slug>_<timestamp>_<uuid8>.pdf`.

Because `sql/` is not versioned, adding support for a new data source means dropping a new `.sql` file into that directory directly (there's no code change needed) — but that file will not travel with a `git clone` of this repo.

## Architecture: the validation pipeline

Everything lives in `app_flask.py` as one process with global mutable state in `app_state` (an in-memory dict — nothing survives a restart except what's already flushed to `logs/`/`reports/`/`expectations/`). There is no database; concurrency is coordinated purely with three `threading.Lock`s (`gx_lock`, `shared_lock`, `sse_lock`), and only **one pipeline can run at a time** (`app_state["pipeline_shared"]` is a single slot, not a per-batch registry).

Request flow: `/` (upload) → `/configure` → `POST /start` → `/pipeline` (SSE-driven progress view) → `/results/<batch_id>` → optional `/waive/<batch_id>` → `/download/<batch_id>`.

`POST /start` spins up a three-stage producer/consumer pipeline as daemon threads, chained through two Python lists on the shared dict (`shared["queue"]`, `shared["ai_queue"]`) rather than a real queue implementation:

1. **`db_checker_worker`** (1 thread) — for every selected `event_type | placement_id` spec, builds a `SELECT 1 ... LIMIT 1` probe via `prepare_spec_sql` and pushes specs that have data onto `shared["queue"]`.
2. **`ai_worker`** (1 thread) — pops from `shared["queue"]`, builds a markdown table of the spec's fields (`Field Name`/`Type`/`Mandatory`/`Allowed Values`, with `group` used to build nested-JSON flatten maps) and sends it through `prompt_template.txt` to Gemini. Retries on 429/500 with exponential backoff, and retries the whole spec (up to 2x) on any other exception. Successful output is parsed as a JSON expectations array and pushed onto `shared["ai_queue"]`.
3. **`gx_worker`** (3 threads) — pops from `shared["ai_queue"]`, calls `run_validation_process`, which re-fetches the real data from Trino (this time via the source `.sql` file plus `prepare_spec_sql`, optionally split into segments if `segment_by` was set), flattens JSON columns per the AI-derived flatten map, registers a pandas datasource/asset in the GX context, applies each expectation, and runs a GX checkpoint. Results are written to `logs/` and appended to `shared["results"]`.

A `finalize_when_done` monitor thread waits for all three stages to drain (or a 1-hour safety timeout, or user cancellation via `POST /stop`), then snapshots `shared` into a `batch` dict, calls `generate_batch_pdf`, and stores it in `app_state["batches"]` / `app_state["batch_history"]`.

Progress is streamed to the browser over SSE (`push_sse` → `/api/stream`, consumed by `templates/pipeline.html`), not polling — `push_sse("tracker_update", ...)` also mutates `shared["tracker"]` in place so a page refresh mid-run still reflects current state.

### Spec sheet contract

Uploaded files must have `event type` and `placement_id` columns (`event_type`/`placement id` are auto-renamed). Optional columns `Field Name`/`Type`/`Mandatory`/`Allowed Values` (aliased from `key`/`Data type`/`M`/`value`) drive AI rule generation; an optional `group` column signals nested-object fields that get flattened to `<parent>_<key>` before both AI generation and GX validation (`flatten_json_columns`).

`placement_id` is parsed as `screen/category/target` (slash-delimited) by `prepare_spec_sql`, which turns it into `screen_name`/`event_category`/`target` WHERE filters against the `event_type` (`click`/`impression`/`custom` get category+target filters; `pageview` only gets the screen filter).

### Result state and waiving

Every GX run's full checkpoint JSON is kept (`log_data`); `extract_failed_from_log` / `get_effective_metrics_from_results` / `get_failed_summary` all recompute pass/fail against a `waived_rules` set (keyed as `"<column>|<expectation_type>"`) so waiving a rule in the UI doesn't require re-running validation — it just changes which failures count, then regenerates the PDF and rewrites `waived_rules` into the on-disk log files.

### PDF generation

`generate_batch_pdf` renders one big HTML string by hand (no Jinja template for the PDF, unlike the web UI which uses `templates/`) and hands it to WeasyPrint. It's called both at pipeline finalization and again on `/waive`.
